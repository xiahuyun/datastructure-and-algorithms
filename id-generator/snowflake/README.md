# id-generator/snowflake — 雪花算法（Snowflake）

在分库分表场景下，`AUTO_INCREMENT` 无法保证跨表唯一，需要专门的 ID 生成器。雪花算法是 Twitter 开源的分布式全局唯一 ID 算法，把一个 64 位整数切分成多段：

```
 0 - 0000000000 0000000000 0000000000 0000000000 0 - 00000 - 00000 - 000000000000
|1位符号位|      41位毫秒时间戳(相对epoch)      | 5位机房 | 5位机器 | 12位序列号 |
```

- **1 位符号位**：固定为 0，保证 ID 恒为正数。
- **41 位时间戳**：相对自定义起始时间 `epoch` 的毫秒偏移，约可用 69 年。
- **10 位机器标识**：拆成 5 位机房 ID + 5 位机器 ID，最多支持 1024 个节点。
- **12 位序列号**：同一毫秒内的自增序列，每毫秒最多生成 4096 个。

## 运行方式

```bash
cd id-generator/snowflake
go run main.go
```

输出大致如下（ID 值每次运行都不同，但结构一致）：

```
== 顺序生成 ==
  ID = 360988596330700800（比上一个更大:true）
  ID = 360988596330700801（比上一个更大:true）
  ...

== ID 结构拆解 ==
  生成时间: 2026-09-23 10:30:00.123 | 机房: 1 | 机器: 2 | 序列号: 4

== 并发唯一性校验 ==
  8 个 goroutine 并发生成 100000 个 ID，重复数: 0
```

## 唯一性怎么保证

只要不同实例的 `(datacenterID, workerID)` 组合不重复，任意机器、任意时刻生成的 ID 都唯一，因为：

1. **时间戳差异**：不同毫秒生成的 ID 高位时间戳不同；
2. **机器标识差异**：同一毫秒内不同机器，靠机器位区分；
3. **序列号**：同一毫秒同一机器内，靠递增序列号区分（每毫秒 4096 个）。

## 并发模型（为什么用 CAS 而不是互斥锁）

朴素实现会用一把 `sync.Mutex` 串行化发号。这里把「上一次毫秒时间戳 + 该毫秒内序列号」打包进单个 `uint64`（高 41 位存时间戳、低 12 位存序列号），再用 `atomic.CompareAndSwapUint64` 一次原子地同时更新两者：

- CAS 成功 → 抢占到这一号，直接拼 ID 返回；
- CAS 失败 → 说明别的 goroutine 抢先了，重读状态重试。

这样就没有锁竞争，高并发下吞吐更高。这也正是题目里「用 CAS 原子锁」想法的落地，只是雪花算法在此基础上多加了一层「时间戳 + 机器位」的语义，让它能横向扩展到多台机器。

## 时钟回拨

雪花算法唯一依赖系统时钟。若 NTP 对时把机器时钟往后拨，`now < lastTimestamp`，就会导致同一时间戳被重复使用。本实现检测到回拨直接返回错误拒绝发号，是 Twitter 原始做法。工业实现还有「等待追平」或「借用未来时间」等更温和的策略。

## 与其它方案的关系

- **类 Snowflake**：百度 UidGenerator（加 RingBuffer 缓存提速）、美团 Leaf-snowflake（用 ZooKeeper 分配 workerID）都是它的变种。
- **类数据库号段**：美团 Leaf-segment、滴滴 TinyID，走「批量取号 + 内存发放」路线，与雪花算法是两条不同的思路。
